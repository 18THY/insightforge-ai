# InsightForge AI — Database Design

This document describes the PostgreSQL data layer implemented in Phase 2:
the schema, relationships, and the reasoning behind key design decisions.
It complements `docs/architecture.md` (system-level design) and
`AGENTS.md` (binding project rules).

> Status: data layer only. No API endpoints read or write these tables
> yet, and no authentication is implemented — see Phase 2 scope below.

---

## 1. Technology

- **PostgreSQL 16** — primary data store.
- **pgvector** (`vector` extension) — similarity search over document
  embeddings for RAG.
- **SQLAlchemy 2.0** (typed declarative models, `Mapped[...]` style) — ORM
  layer.
- **Alembic** — schema migrations, autogenerated from the SQLAlchemy
  models and hand-reviewed before being applied.

All 18 required tables are implemented in `backend/app/db/models/`, one
module per domain area, and registered in `backend/app/db/models/__init__.py`
so Alembic's `--autogenerate` sees the complete schema.

---

## 2. Conventions applied to every table

- **Primary key**: `id UUID`, generated client-side (`uuid.uuid4()`) at
  the Python/ORM layer rather than via a database default. This keeps ID
  generation portable and available before a row is flushed.
- **Timestamps**: `created_at` and `updated_at`, both
  `TIMESTAMP WITH TIME ZONE`, defaulting to `now()` at the database level
  (`updated_at` also updates on every `UPDATE`). The one exception is
  `audit_logs`, which has `created_at` only — audit records are
  append-only and must never be modified after being written.
- **Naming convention**: constraints and indexes follow a fixed naming
  convention (`pk_<table>`, `fk_<table>_<column>_<referred_table>`,
  `uq_<table>_<columns>`, `ck_<table>_<name>`, `ix_<column_label>`) so
  that every future migration references stable, predictable names
  instead of database-assigned ones.
- **Enum-like fields** (`status`, `role`, `severity`, etc.) are plain
  `VARCHAR` columns with a `CHECK` constraint listing the valid values,
  rather than native PostgreSQL enum types. This keeps adding a new valid
  value a simple constraint migration instead of an enum-altering one.

## 3. Organization-level isolation

Organizations are the tenant boundary for the whole platform. Every
business-data table carries an `organization_id` foreign key to
`organizations.id`, indexed, so that every query can (and, at the service
layer in a later phase, must) be scoped to the caller's organization.

Two deletion patterns are used for foreign keys, chosen per relationship:

| Pattern | Used for | Rationale |
|---|---|---|
| `ON DELETE CASCADE` | `organization_id` on nearly every table; `dataset_id → dataset_columns`; `document_id → document_chunks`; `conversation_id → ai_messages`; `order_id → payments` | If the owning organization (or parent record) is deleted, its dependent data has no remaining meaning and should be removed with it. |
| `ON DELETE SET NULL` | User-attribution columns (`created_by`, `uploaded_by`, `analytics_queries.user_id`, `ai_conversations.user_id`, `audit_logs.user_id`); `orders.customer_id`, `orders.product_id`; `anomalies.dataset_id`, `forecasts.dataset_id` | Removing a user or a source dataset/customer/product shouldn't destroy business records that reference it — the record survives with the reference cleared, preserving history. |

`audit_logs.organization_id` uses `CASCADE` rather than `SET NULL`: once
an organization is gone, its audit trail has no further use scoped
outside that organization, so it is removed with it (this was verified in
testing — see §7).

This was verified functionally: deleting an `Organization` row cascades
correctly through members, datasets (and their columns), documents (and
their chunks), customers, orders (and their payments), and audit logs,
while unrelated rows (e.g. the `User` who owned the organization) are
untouched.

## 4. Entity groups and relationships

### 4.1 Identity & tenancy

- **`organizations`** — tenant root. `name`, unique `slug`.
- **`users`** — platform users. Unique `email`. Carries a nullable
  `hashed_password` column reserved for a later authentication phase;
  no auth logic exists yet.
- **`organization_members`** — join table between `users` and
  `organizations`, carrying a `role` (`owner` / `admin` / `member` /
  `viewer`, enforced by `CHECK`). Unique on `(organization_id, user_id)` —
  one membership row per user per organization.

```
organizations 1───* organization_members *───1 users
```

### 4.2 Datasets

- **`datasets`** — one row per uploaded business dataset. Unique on
  `(organization_id, name)`. `status` tracks the profiling lifecycle
  (`uploaded → profiling → ready`, or `error`).
- **`dataset_columns`** — one row per profiled column of a dataset:
  `name`, inferred `data_type`, `ordinal_position`, `is_nullable`. Unique
  on `(dataset_id, name)`.

```
datasets 1───* dataset_columns
```

### 4.3 Core business entities

- **`customers`**, **`products`** — organization-scoped reference data,
  each with an optional `external_id` (the identifier from the source
  system/upload) unique per organization.
- **`orders`** — references `customers` and `products` (both nullable,
  `SET NULL` on delete, since generic uploaded data may not always map
  cleanly to both). Unique `(organization_id, external_id)`.
- **`payments`** — belongs to an `order` (`CASCADE` on delete — a
  payment has no meaning without its order).

```
customers 1───* orders *───1 products
orders 1───* payments
```

### 4.4 Documents & RAG

- **`documents`** — one row per uploaded business document.
- **`document_chunks`** — chunked text extracted from a document, each
  with an `embedding vector(768)` column (pgvector), matching Gemini's
  `text-embedding-004` dimensionality. `organization_id` is denormalized
  onto this table (copied from the parent document) so that similarity
  search can filter by tenant directly, without a join, on every query.
  An **HNSW index** (`vector_cosine_ops`) is defined on `embedding` for
  approximate nearest-neighbour search. Unique on
  `(document_id, chunk_index)`.

```
documents 1───* document_chunks
```

### 4.5 AI interaction & traceability

- **`analytics_queries`** — one row per natural-language question asked
  of the data: the `question`, the `generated_sql` the AI proposed, its
  validation/execution `status`, and a `result_summary`. This table is
  the audit trail required for AGENTS.md's rule that AI-generated SQL
  must be validated and traceable — the actual validation/execution logic
  is implemented in a later phase; this table only provisions where that
  record is stored.
- **`ai_conversations`** / **`ai_messages`** — general AI chat history
  (e.g. report-drafting or Q&A conversations), independent of the
  SQL-generation flow. `ai_messages.role` is constrained to
  `user` / `assistant` / `system` / `tool`.

```
ai_conversations 1───* ai_messages
```

### 4.6 ML outputs

- **`anomalies`** — detected anomalies per metric, with `severity`
  (`low`/`medium`/`high`/`critical`), the observed `value` and
  `expected_value`, and an optional link back to the source `dataset`.
- **`forecasts`** — predicted values per metric per `forecast_date`, with
  optional confidence bounds (`lower_bound`, `upper_bound`) and the
  `model_name` used.

Both are optionally linked to `datasets` via `SET NULL` on delete, so
historical anomaly/forecast records are retained even after the source
dataset is removed.

### 4.7 Reports & audit

- **`reports`** — AI-generated business reports (`title`, `summary`,
  `content`, lifecycle `status`: `draft` / `generated` / `published`).
- **`audit_logs`** — append-only log of important operations
  (`action`, optional `resource_type` / `resource_id`, a free-form
  `metadata` JSONB column — mapped to the Python attribute `meta` since
  `metadata` is reserved by SQLAlchemy's declarative base — and
  `ip_address`). Both `organization_id` and `user_id` are nullable, to
  accommodate system-level events not scoped to one tenant or actor.

## 6. Migrations

Managed with Alembic, configured in `backend/alembic.ini` /
`backend/alembic/env.py`. The database URL is never hardcoded — `env.py`
reads it from `app.core.config.Settings` (i.e. the `DATABASE_URL`
environment variable / `.env`), consistent with AGENTS.md's "no hardcoded
secrets" rule.

**Initial migration**: `backend/alembic/versions/7b4df9e24d1b_initial_schema.py`
— creates all 18 tables plus:
- `CREATE EXTENSION IF NOT EXISTS vector` (run before any table is
  created, since `document_chunks.embedding` depends on the type it
  provides)
- The HNSW index on `document_chunks.embedding`

To apply migrations:

```bash
cd backend
alembic upgrade head
```

To create a new migration after changing models:

```bash
cd backend
alembic revision --autogenerate -m "describe the change"
# review the generated file before applying
alembic upgrade head
```

## 7. Verification performed (Phase 2)

All of the following were run against a real PostgreSQL 16 instance with
the `vector` extension enabled:

1. `alembic upgrade head` — applied cleanly, no errors.
2. `\dt` — confirmed all 18 tables (+ `alembic_version`) exist.
3. `\d <table>` on several tables — confirmed column types, primary
   keys, foreign keys (with correct `ON DELETE` behavior), unique
   constraints, check constraints, and indexes match the models exactly.
4. `alembic downgrade base` then `alembic upgrade head` — confirmed a
   clean, reversible round-trip with no errors.
5. `alembic check` — confirmed **no drift** between the models and the
   migration (no pending autogenerate changes).
6. A functional smoke test via the ORM:
   - Inserted an organization, user, membership, dataset (+ column),
     customer, order, and audit log; confirmed relationships
     (`dataset.columns`, `order.customer`) resolve correctly.
   - Confirmed the `uq_organizations_slug` unique constraint rejects a
     duplicate slug (`IntegrityError`).
   - Confirmed the `ck_organization_members_role_valid` check constraint
     rejects an invalid role (`IntegrityError`).
   - Inserted document chunks with random 768-dimension embeddings and
     ran a cosine-distance similarity query (`ORDER BY embedding <=>
     query_vector`) — returned correctly ranked results.
   - Deleted an organization and confirmed cascade deletion of its
     members, datasets, dataset columns, documents, document chunks,
     customers, orders, and audit logs, while the unrelated `User` row
     was retained (attribution FKs are `SET NULL`, not cascaded).
7. The database was reset to a clean, empty schema (`downgrade base` →
   `upgrade head`) after verification, so it is handed off with no test
   data in it.

## 8. Explicitly out of scope for Phase 2

Per the phase instructions, the following are **not** implemented yet,
even though some tables provision columns for them:

- Authentication (password hashing, login, tokens) — `users.hashed_password`
  exists as a column only.
- Any API endpoint reading or writing these tables.
- NL-to-SQL generation, validation, or execution logic.
- Data upload/profiling logic that would populate `datasets` /
  `dataset_columns`.
- RAG chunking/embedding generation logic.
- Anomaly detection / forecasting computation logic.
- Report generation logic.
